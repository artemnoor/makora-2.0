# Локальный дашборд разработки

Запуск из корня клона

```powershell
$env:DASHBOARD_DATA_DIR = Join-Path $env:LOCALAPPDATA "Codex/OpenCode Dashboard"
node ./dashboard/server.cjs
```

Откройте [дашборд](http://127.0.0.1:18741/). Рабочие сессии остаются в Codex и OpenCode Desktop. Дашборд показывает проект, этап, задачи, решения, отдельные рабочие копии и результаты прогонов E Verified Batch.

## Работа из Codex

- «Начни задачу в проекте …» — зарегистрируй проект в дашборде по его каноническому пути, поставь этап `brief`. Перед архитектурой найди существующую запись проекта. Сохраняй критерии и зависимости в задачах, выставляй фазу на момент перехода и привязывай run ID к связанной задаче.
- «Добавь идею: …» — выполни [приём идеи](idea-intake.SKILL.md). Используй выбранный проект в текущей папке или указанный пользователем. Если нет однозначного проекта, запроси его название или путь. Сохрани исходный текст и предложи момент реализации. Для планируемой работы укажи зависимость, когда она известна. Дождись решения на дашборде до включения идеи в план. Не добавляй идею на основании обычного обсуждения.
- «Продолжи проект …» — прочитай актуальное состояние через `control.cjs state`, определи следующий разрешённый переход и возобнови работу. Решение пользователя привязано к конкретной лаборатории, идее или макету.
- Перед передачей задания используй профиль конкретной модели из `dashboard/profiles/`. Проверь, что после адаптации сохранены исходные требования, контракты, критерии приёмки и `writeScope`. Модель остаётся выбранной пользователем или регламентом проекта.

Команды для Codex:

```powershell
node ./dashboard/control.cjs state
node ./dashboard/control.cjs action "<action.json>"
```

Для `action` передавай JSON UTF‑8. Используй `project.add`, `project.phase`, `task.put` и профильные команды наблюдения. При завершении сессии переводи задачу на ревью. Отмечай её принятой после независимой проверки Codex, через действие `task.accept` с полями `projectId`, `id` и `evidence`. В доказательстве укажи путь к diff, журналу тестов или манифесту сборки.

## Лаборатории

Предлагай изолированное демо, если оно поможет проверить рискованный сценарий отдельно. Зафиксируй сценарий, критерии и раздельные области кода функции и демонстрации. Запуск разработки лаборатории следует за одобрением пользователя в дашборде. Код пишет OpenCode в подходящей рабочей копии.

Зарегистрируй локальный запуск через `lab.configure`: рабочий путь, поддерживаемый рантайм, массив аргументов, доказательство из сборки. Используй `{port}` для отдельного локального порта и `{data}` для изолированных тестовых данных. Пользователь запускает демо и принимает сценарий или возвращает замечание.

Сохраняй код модуля и тесты как отдельный результат исполнителя с собственной зоной записи. Демонстрационные страницы и данные держи в отдельном результате. При интеграции передавай в `assemble` только исполнителя модуля и тестов. Если прототип уже смешал их с демо, выдай OpenCode отдельное задание на перенос модуля и тестов. Перед приёмкой прогоняй общие сценарии и `verify` по регламенту E Verified Batch.

## Референсы, Figma и браузерная приёмка

1. Создай фронтенд-задачу и карточку дизайна. Сохрани ссылки на референсы и для каждого — решение, которое предлагаешь взять. Отметь готовность референсов, чтобы пользователь выбрал направление в дашборде.
2. После первого решения работай в разрешённом черновике Figma. Перед Figma-действием используй предусмотренный для него навык. Загрузи отобранные материалы, собери редактируемые компоненты и состояния, затем экранные фреймы для десктопа и телефона. Сохрани ссылку на проверяемую версию макета.
3. Дождись утверждения макета в дашборде. Передай OpenCode фреймы, контракт API, границы записи и критерии. Включи состояния загрузки, пустого результата и ошибки там, где они нужны.
4. Второй исполнитель проверяет браузерную реализацию относительно зафиксированных фреймов. В доказательствах укажи проверенные размеры, клавиатурный сценарий, основные состояния и найденные расхождения. Codex принимает результат после общей проверки E Verified Batch.

Figma-действия выполняются из подключённого чата с правом редактирования нужного файла. При отсутствии доступа зафиксируй конкретный блокер в задаче, чтобы пользователь мог открыть файл или выдать доступ. Модель не переходит к вёрстке до второго решения.

## Профили моделей

```powershell
node ./dashboard/control.cjs idea "<project-id>" "<исходный текст идеи>"
node ./dashboard/control.cjs compile big-pickle "<ticket.json>"
node ./dashboard/control.cjs compile sol "<ticket.json>"
```

Команда `idea` сохраняет исходный текст. Для предложения этапа и связи с задачей отправь `idea.add` через `action` с `proposal` и `afterTaskId`. Для тикета профиля передай `goal`, `context`, `contract`, `writeScope`, `criteria`, `report`. Компилятор возвращает версию и готовый промпт для указанной модели. Формат описан в [справке профилей](profiles/README.md). Источники и проверяемые гипотезы собраны в [заметках по профилям](profiles/SOURCES.md).

## Рабочие копии и сессии

Браузер обновляет состояние панели периодически, считывая локальные манифесты и журналы. Run ID, путь рабочей копии и ID дочерней сессии позволяют сопоставить карточку с OpenCode Desktop. Для нового Git-проекта с коммитом-основанием запрашивай `mode: "worktree"`. Если у проекта ещё нет коммита, используй предусмотренный E Verified Batch режим отдельной копии и показывай этот режим в панели. Дашборд не меняет Git-ветки и не создаёт коммиты.

По умолчанию сервис работает без Figma. Когда Codex подтвердил доступ к черновику через подключение Figma, включи учёт подтверждённого подключения для этого запуска, стартовав сервер с `DASHBOARD_FIGMA_CONNECTED=1`. Эта переменная фиксирует результат проверки подключения. Автоматическую проверку прав выполняет подключённый чат. Два человеческих решения остаются обязательными.

## Первый запрос в новом проекте

Открой папку проекта в новом чате Codex и отправь:

> Выполни задачу [описание] через E Verified Batch. Веди проект в локальном дашборде. Спроектируй архитектуру и контракты, отдай каркас и весь код OpenCode, параллельные тикеты разнеси по Git worktrees. Сначала сам проверь каркас, а после работы исполнителей проверь diff, сборку и критерии. Для сложного сценария предложи лабораторию и дождись решения. Фронтенд веди через референсы и Figma с двумя моими подтверждениями.

Для модели вне реестра используй её официальное руководство и проведи одинаковый контрольный тикет до добавления нового профиля. Запиши версию, точный ID модели, формат задания и источники. Не применяй профиль другой модели по сходству имени.
