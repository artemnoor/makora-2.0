# Локальный дашборд разработки

Запуск из корня клона

```powershell
npm ci --ignore-scripts
$env:DASHBOARD_DATA_DIR = Join-Path $env:LOCALAPPDATA "Codex/OpenCode Dashboard"
node ./dashboard/server.cjs
```

Откройте [дашборд](http://127.0.0.1:18741/). Рабочие сессии остаются в Codex и OpenCode Desktop. Дашборд показывает проект, этап, задачи, решения, отдельные рабочие копии и результаты прогонов E Verified Batch.

## Работа из Codex

- «Начни задачу в проекте …» — зарегистрируй проект в дашборде по его каноническому пути, поставь этап `brief`. Перед архитектурой найди существующую запись проекта. Сохраняй критерии и зависимости в задачах, выставляй фазу на момент перехода и привязывай run ID к связанной задаче.
- «Добавь идею: …» — выполни [приём идеи](idea-intake.SKILL.md). Используй выбранный проект в текущей папке или указанный пользователем. Если нет однозначного проекта, запроси его название или путь. Сохрани исходный текст и предложи момент реализации. Для планируемой работы укажи зависимость, когда она известна. Дождись решения на дашборде до включения идеи в план. Не добавляй идею на основании обычного обсуждения.
- «Продолжи проект …» — прочитай актуальное состояние через `control.cjs state`, определи следующий разрешённый переход и возобнови работу. Решение пользователя привязано к конкретной лаборатории, идее или макету.
- Перед передачей задания используй профиль конкретной модели из `dashboard/profiles/`. Проверь, что после адаптации сохранены исходные требования, контракты, критерии приёмки и `writeScope`. Модель остаётся выбранной пользователем или регламентом проекта.

Команды для Codex:

```powershell
node ./dashboard/control.cjs state
node ./dashboard/control.cjs action "<action.json>"
```

Для `action` передавай JSON UTF‑8. Используй `project.add`, `project.phase`, `task.put` и профильные команды наблюдения. При завершении сессии переводи задачу на ревью. Отмечай её принятой после независимой проверки Codex, через действие `task.accept` с полями `projectId`, `id` и `evidence`. В доказательстве укажи путь к diff, журналу тестов или манифесту сборки.

## Лаборатории

Предлагай изолированное демо, если оно поможет проверить рискованный сценарий отдельно. Зафиксируй сценарий, критерии и раздельные области кода функции и демонстрации. Запуск разработки лаборатории следует за одобрением пользователя в дашборде. Код пишет OpenCode в подходящей рабочей копии.

Зарегистрируй локальный запуск через `lab.configure`: рабочий путь, поддерживаемый рантайм, массив аргументов, доказательство из сборки. Используй `{port}` для отдельного локального порта и `{data}` для изолированных тестовых данных. Пользователь запускает демо и принимает сценарий или возвращает замечание.

Сохраняй код модуля и тесты как отдельный результат исполнителя с собственной зоной записи. Демонстрационные страницы и данные держи в отдельном результате. При интеграции передавай в `assemble` только исполнителя модуля и тестов. Если прототип уже смешал их с демо, выдай OpenCode отдельное задание на перенос модуля и тестов. Перед приёмкой прогоняй общие сценарии и `verify` по регламенту E Verified Batch.

Рекурсивный режим хранит версии дерева, попытки, сборки и ревью в SQLite. Его настройки и эксплуатационные проверки описаны в [документации рекурсивных лабораторий](../docs/recursive-labs.md).

## Аутсорс

Вкладка **Аутсорс** позволяет поручить самостоятельный модуль внешней модели через переносимое ТЗ. Внешнему исполнителю достаточно скачанных файлов. Подключение к Makora ему не требуется.

1. Подготовьте ТЗ по [навыку outsource-brief](../skills/outsource-brief/SKILL.md). Укажите цель, контекст, границы, критерии, OpenAPI 3.0/3.1 и новый относительный каталог. Его родитель должен уже существовать в зарегистрированном проекте.
2. Скачайте ТЗ и OpenAPI, проверьте содержимое и передайте исполнителю. Экспорт содержит введённые вами поля и формат ответа. Makora сама не читает исходники проекта для экспорта.
3. Загрузите ZIP. В корне должны находиться `outsource.json` с данными из `returnZip`, копия `openapi.json` и папка `module/` с результатом. Можно загрузить архив, скачанный с GitHub, если у него такая структура корня. Предельный размер ZIP — 10 МиБ, после распаковки — 32 МиБ, не более 512 записей.
4. Проверьте файлы в промежуточном каталоге. До приёмки ZIP можно заменить. Внесите результаты ревью и тестов и примите архив с указанным SHA-256.
5. Нажмите «Добавить файлы в проект». В новом каталоге появятся `openapi.json` и `module/`. Подключите реализацию в приложении через согласованный API и прогоните тест вызова из потребителя. Запуск, коммиты и публикация кода управляются отдельно.

Для импорта установите зависимость в корне Makora: `npm ci --ignore-scripts`.

### CLI и HTTP

`node dashboard/control.cjs action <файл.json>` создаёт задание, принимает и интегрирует результат. Пример создания задания:

```json
{
  "action": "outsource.create",
  "projectId": "<id проекта>",
  "title": "Счётчик",
  "goal": "Отдать число обработанных записей",
  "context": "Источником служат синтетические данные",
  "boundaries": "Модуль владеет GET /count. Хранилище приложения вне его ответственности",
  "targetPath": "modules/counter",
  "criteria": ["GET /count возвращает 200 и целое неотрицательное поле count"],
  "openapi": {
    "openapi": "3.1.0",
    "info": { "title": "Counter", "version": "1.0.0" },
    "paths": {
      "/count": {
        "get": {
          "responses": {
            "200": {
              "description": "Число обработанных записей",
              "content": {
                "application/json": {
                  "schema": {
                    "type": "object",
                    "required": ["count"],
                    "properties": { "count": { "type": "integer", "minimum": 0 } }
                  }
                }
              }
            }
          }
        }
      }
    }
  }
}
```

`GET /api/outsources/<projectId>/<id>/brief` скачивает ТЗ, `GET …/contract` отдаёт OpenAPI. Загрузку выполняет `POST …/archive` с телом ZIP и `Content-Type: application/zip`.

```powershell
$job = "http://127.0.0.1:18741/api/outsources/<projectId>/<id>"
curl.exe -fS "$job/brief" -o brief.json
curl.exe -fS "$job/contract" -o openapi.json
curl.exe -fS -H "Content-Type: application/zip" --data-binary "@module.zip" "$job/archive"
```

`outsource.accept` принимает `projectId`, `id`, `sha256` из `outsource.artifact.sha256` и строку `evidence`. `outsource.integrate` принимает те же поля без `evidence`. Повтор с тем же проверенным хешем идемпотентен. Для следующей версии после приёмки создайте новое задание с новым каталогом. Состояние и файлы ревью сохраняются в каталоге данных дашборда.

## Работа с Figma через плагин Codex

Codex работает в Figma через официальный плагин Figma в настольном чате. Для проверки авторизации вызови `whoami`. Авторизация учётной записи подтверждается ответом плагина. Чтение и редактирование зависят от прав на конкретный файл. Дашборд хранит результат работы с файлом, а плагин выполняет действия в Figma.

1. Создай фронтенд-задачу и карточку дизайна. Найди референсы, укажи источники и конкретные решения. Передай ссылки в `design.advance` с шагом `references_ready`. Пользователь подтверждает направление в дашборде.
2. После подтверждения открой разрешённый файл Figma либо создай черновик в согласованной команде. Для создания файла прочитай `figma-create-new-file`. Перед чтением и изменением конкретного файла создай сессию Figma, когда инструмент доступен, и передавай её ID в вызовах. Для записи в макет используй `use_figma` с навыками `figma-use` и `figma-generate-design`. Добавь утверждённые референсы, компоненты, состояния и экранные фреймы. Для чтения известных фреймов используй `get_design_context` после загрузки навыка `figma-design-to-code`. Если плагин не смог прочитать или изменить файл, сохрани конкретную причину в задаче.
3. После успешной проверки фреймов зарегистрируй файл в карточке через `control.cjs action` и `design.figma.sync`. Укажи фактический ключ файла и ID фреймов, полученные от плагина. Пользователь открывает ссылки на фреймы в дашборде и утверждает макет там. Если макет изменён до утверждения, повторно проверь фреймы и синхронизируй актуальные данные.
4. После второго решения выдай OpenCode задачу со ссылками на утверждённые фреймы, контрактом API, границами записи и критериями. Поручи независимому исполнителю проверить браузерную реализацию, состояния и размеры экрана. Codex принимает результат по общему регламенту E Verified Batch.

Пример локального действия. Значения в примере заменяются данными из ответа плагина.

```json
{
  "action": "design.figma.sync",
  "projectId": "<project-id>",
  "id": "<design-id>",
  "fileKey": "<figma-file-key>",
  "frames": [
    { "nodeId": "12:34", "name": "Desktop" },
    { "nodeId": "12:56", "name": "Mobile" }
  ]
}
```

Дашборд хранит ключ, ссылки и факт последней синхронизации. Для просмотра или записи в Figma Codex использует текущую авторизацию плагина и проверяет доступ к файлу в чате. Для передачи источников и изображений в Figma используй только материалы, согласованные для этого макета.

## Профили моделей

```powershell
node ./dashboard/control.cjs idea "<project-id>" "<исходный текст идеи>"
node ./dashboard/control.cjs compile big-pickle "<ticket.json>"
node ./dashboard/control.cjs compile sol "<ticket.json>"
```

Команда `idea` сохраняет исходный текст. Для предложения этапа и связи с задачей отправь `idea.add` через `action` с `proposal` и `afterTaskId`. Для тикета профиля передай `goal`, `context`, `contract`, `writeScope`, `criteria`, `report`. Компилятор возвращает версию и готовый промпт для указанной модели. Формат описан в [справке профилей](profiles/README.md). Источники и проверяемые гипотезы собраны в [заметках по профилям](profiles/SOURCES.md).

## Рабочие копии и сессии

Браузер обновляет состояние панели периодически, считывая локальные манифесты и журналы. Run ID, путь рабочей копии и ID дочерней сессии позволяют сопоставить карточку с OpenCode Desktop. Для нового Git-проекта с коммитом-основанием запрашивай `mode: "worktree"`. Если у проекта ещё нет коммита, используй предусмотренный E Verified Batch режим отдельной копии и показывай этот режим в панели. Дашборд не меняет Git-ветки и не создаёт коммиты.

## Первый запрос в новом проекте

Открой папку проекта в новом чате Codex и отправь:

> Выполни задачу [описание] через E Verified Batch. Веди проект в локальном дашборде. Спроектируй архитектуру и контракты, отдай каркас и весь код OpenCode, параллельные тикеты разнеси по Git worktrees. Сначала сам проверь каркас, а после работы исполнителей проверь diff, сборку и критерии. Для сложного сценария предложи лабораторию и дождись решения. Фронтенд веди через референсы и Figma с двумя моими подтверждениями.

Для создания или обновления профиля используй [навык model-prompt-profile](../skills/model-prompt-profile/SKILL.md). Он описывает поиск официальной документации и опыта пользователей, проверку гипотез на сопоставимых тикетах и регистрацию версии. Вызови его, когда выбранная модель ещё отсутствует в реестре или пользователь попросил обновить профиль.
