# opencode/big-pickle — исполнитель

Профиль упаковывает тикет для изолированного агента OpenCode. Модель по умолчанию —
`opencode/big-pickle`; при ошибке бесплатной модели сообщить причину и сохранить
сессии, без автоматического переключения провайдера.

## Общий контракт тикета

Все тикеты имеют одни и те же поля: `goal`, `context`, `contract`, `writeScope`,
`criteria`, `report`. При компиляции они сохраняются дословно. Меняется только
упаковка (заголовки, форматирование, порядок секций) — не содержание. Персональные
характеристики, роли-персонажи и «улучшающие» переформулировки не добавлять.

- `goal` — цель и независимый случай приёмки.
- `context` — inbound-контекст: ссылки на источники, предыдущие решения, ограничения.
- `contract` — наблюдаемый контракт интерфейса/API и критерии останова.
- `writeScope` — точные пути файлов/каталогов, закреплённые за исполнителем.
- `criteria` — зафиксированная до запуска матрица критериев с наблюдаемым результатом.
- `report` — что вернуть: ID сессии, файлы, команды, результаты, ограничения.

## Официальные рекомендации

- Работать только в своей рабочей копии и только в назначенных файлах.
- Критерии приёмки фиксируются до запуска и не переписываются после ответов исполнителей.
- Выполнить проверки своей задачи, вернуть изменения на ревью, коммиты не создавать.
- Дополнительные навыки не подключать без явного указания в задании.
- Возвращать ID сессии, список файлов, выполненные команды, результаты и ограничения.

## Эмпирические наблюдения

- Проверка зоны записи выполняется после сканирования changedPaths, а не как песочница.
- Родительская сессия запускает одного дочернего агента; ID подтверждается по событиям
  `background_wait`/`subagent` и экспорту сессии с совпадающим `parentID`.
- В установленном OpenCode Desktop 2.3.0 продолжение сессии не гарантировано: при
  неподтверждённой идентичности нужен свежий scopes-запуск, а не повтор той же сессии.
- Успешный код выхода CLI и самоотчёт доказательством результата не являются.

Отличать явно: раздел «Официальные рекомендации» — задокументированные правила,
раздел «Эмпирические наблюдения» — локальные замеры и наблюдения, не норма.

## Рубрика оценки

| Критерий | Наблюдаемый факт | Доказательство | Серьёзность |
| --- | --- | --- | --- |
| Поля сохранены | Все шесть полей тикета присутствуют дословно | Скомпилированный prompt | blocker |
| Зона записи | Изменения только внутри `writeScope` | `summary.json`, diff | major |
| Верификация сессии | Ровно один дочерний ID, совпадающий `parentID` | `*.export.json` | blocker |
| Проверки | Команды задачи выполнены, вывод приложен | `*.process.log` | major |
| Отчёт | Указаны сессия, файлы, команды, ограничения | Ответ исполнителя | minor |

Завершённая сессия не равна принятому результату: приёмка фиксируется человеком
после просмотра diff и интегрированных тестов.

## Приём идей из других чатов

Идеи приходят явным действием `idea.add` с текстом и идентификатором проекта.
Нормализованный текст в рамках проекта идемпотентен. Идея остаётся идеей до явного
`idea.decide`; решение `deferred` не запускает работу и не меняет фазу.

## Передача этапа Figma

Последовательность: `references_ready` → `references_approved` → `figma_ready` →
`figma_approved` → `implemented` → `reviewed`. Два человеческих шлюза обязательны:

1. `references_approved` — человек подтверждает источники и ссылки до работы в Figma.
2. `figma_approved` — человек подтверждает ссылку Figma и кадры до реализации.

Если подключение к Figma отсутствует, этап `figma_ready` явно блокируется: ссылка
и кадры не выдумываются, переход к `implemented` невозможен. На каждом шаге
фиксируется артефакт или заметка; пропуск шлюза запрещён.

## Запреты

- Дашборд не редактирует исходный проект и не запускает/останавливает агентов OpenCode.
- Не называть результат «принятым» или «активным» на основе устаревших данных наблюдателя.
- Не добавлять текст сверх сохранённых полей тикета.
