# E Verified Batch

[[00 — Makora]] · [[01 — Архитектура и роли]] · [[04 — Вложенные лаборатории]] · [[06 — Рабочие копии и сборка]] · [[09 — Модели и тикеты]]

E Verified Batch выдаёт независимые задачи OpenCode и собирает доказательства по каждому исполнителю. Один батч работает от одного исходного состояния. Зависимая работа получает новую композицию входов в рекурсивном режиме или отдельный батч после приёмки в ручном потоке.

## Что происходит по шагам

1. **Чтение плана.** Для каждого исполнителя валидируются имя, промпт, модель, агент и область записи. Лимит самостоятельного батча — три исполнителя. Рекурсивный план по умолчанию выбирает максимум двух. Пересечения заявленных областей отклоняются заранее.
2. **Подготовка.** Создаётся каталог `run-…` с исходным снимком, рабочими копиями, манифестом и заданиями `<name>.prompt.txt`. Makora использует локальный сервис OpenCode Desktop.
3. **Запуск.** Для одного исполнителя CLI запускает родителя `build`. Родителю поручено один раз вызвать дочернего агента, по умолчанию `general`, и передать ему тикет. Код пишет дочерний агент. Родитель ожидает отчёт. События фиксируются в `<name>.jsonl`, вывод обвязки — в `<name>.process.log`.
4. **Верификация сессий.** Из событий извлекаются parent ID и ожидаемый одиночный child ID. Экспорт дочерней сессии проверяется на соответствие ID, связи `parentID`, терминальному исходу и завершённому ответу. Самоотчёт агента служит дополнительным контекстом.
5. **Верификация файлов.** Исходный снимок и копия сравниваются. Для подтверждённых изменений сохраняются diff и хеши. Gate сопоставляет фактические правки с зонами и результатами соседних исполнителей. `summary.json` содержит итоги по каждому работнику и причины блокировки.
6. **Сборка.** `assemble` берёт выбранных подтверждённых исполнителей. `verify` проверяет получившуюся папку по манифесту. Интеграционные тесты и приёмка закрывают оставшиеся критерии. См. [[06 — Рабочие копии и сборка]].

## Области записи

`writeScope` — список относительных файлов и каталогов. Каталог обязательно заканчивается на `/`. Например, `["src/server.cjs", "test/"]`. Абсолютные пути, выход через `..`, подстановки и пересекающиеся записи отклоняются. Сравнение областей учитывает регистр Windows и границы компонентов пути. Точное совпадение пути и конфликт файла с путём-потомком считаются пересечением.

Gate анализирует добавления, удаления и изменения после исполнения. Он блокирует попадание правок за пределами области в сборку и замечает конфликты между работниками. У старых самостоятельных планов поле могло отсутствовать, и фактические конфликты всё равно проверяются. В рекурсивном плане область обязательна. Явные `null` и пустой список недопустимы. Копии и gate изолируют рабочие результаты. Ограничения доступа процесса к остальным файлам определяются правами ОС и настройками OpenCode.

## Управляемый OpenCode

Рекурсивный адаптер закреплён за Desktop CLI **2.3.0**. Он проверяет loopback-адрес и локальный контракт OpenAPI. Перед отправкой в существующую родительскую сессию фиксирует её ID и каталог в файле владения. При отмене находит принадлежащую запуску сессию и её детей, очищает очереди их ввода и вызывает `session.interrupt` с `resume=false`. Остановка подтверждается по активным сессиям, очередям и терминальным исходам. Исчезновение локального CLI само по себе этого не доказывает.

## Ручные команды

```powershell
node ./workers.cjs batch "<корень проекта>" "<plan.json>"
node ./workers.cjs assemble "<каталог run>" server ui
node ./workers.cjs verify "<каталог сборки>"
node ./workers.cjs retry "<каталог run>" server "<уточненный prompt.txt>"
```

`retry` — самостоятельная команда продолжения конкретной записанной дочерней сессии. Она проверяет предыдущий артефакт, требует новое задание для результата, уже завершённого и отклонённого на ревью, и использует блокировку от второго одновременного повтора. OpenCode может отказаться продолжать сессию. Тогда команда сохраняет логи и требует свежий батч с уточнённым заданием. Рекурсивное перепланирование ведёт отдельную историю попыток и свежих рабочих копий.
