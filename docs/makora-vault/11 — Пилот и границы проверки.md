# Пилот и границы проверки

[[00 — Makora]] · [[04 — Вложенные лаборатории]] · [[06 — Рабочие копии и сборка]] · [[10 — Эксплуатация и диагностика]]

Проверки этой заметки относятся к текущей работе в локальном клоне Makora. Живой OpenCode и тестовый исполнитель дали разные результаты. Ниже каждый вывод привязан к своему прогону.

## Как было разбито одно задание

Задача — подготовить каталог с авторизацией, SQLite и обработчиками API. Критерии включали отклонение запроса без правильного токена, запись и чтение данных и обработку некорректного запроса. Чат сформировал дерево из семи узлов.

```text
root — интеграция каталога и итоговые тесты
├─ core — авторизация и хранилище
│  ├─ auth — проверка токена
│  └─ records — вложенная лаборатория SQLite
│     └─ catalog — реализация хранилища
└─ delivery — лаборатория API, зависит от core
   └─ service — обработчики, наследуют зависимость от core
```

**Почему именно так.** Токен и хранилище меняют разные файлы и могут стартовать с одной базы. Вложенная ветка SQLite имеет собственную проверку. Общая ветка `core` даёт принимаемый контракт для API. Зависимость записана на `delivery`, чтобы вход действовал и для всех её будущих листьев.

## Что произошло в тестовом исполнении

Записи SQLite подтвердили порядок. На тестовой стороне использовались подготовленные результаты исполнителя, а композиция, планирование, проверки Node.js и ревью шли через рабочие механизмы Makora.

| Шаг | Операция | Наблюдение |
|---:|---|---|
| 1 | Батч `auth + catalog` | Два листа на разной глубине получили одинаковую базу. Зависимый `service` ожидал. |
| 2 | Интеграция `records` | SQLite прошёл проверки вложенной ветки. |
| 3 | Интеграция `core` | Авторизация и вложенный результат SQLite собраны вместе. |
| 4 | Ревью `core` | В текущем чате изучены изменения и независимо повторены два теста. После приёмки появился допустимый вход для API. |
| 5 | Батч `service` | Планировщик выдал задачу с одним принятым входным артефактом ветки `core`. |
| 6 | Интеграция `delivery` и `root` | Выполнены проверки API и совокупные проверки проекта. |
| 7 | Ревью `root` | В чате повторены три финальных теста. Все семь узлов приняты. |

Итого — три попытки листьев, четыре интеграции, два ревью из чата, все три финальных теста прошли. В Chromium подтверждено раскрытие дерева до четвёртого уровня. Прогон `519bd099-a216-4293-9e65-c4f188357e3a`. Его диагностический дашборд был запущен на порту 18746.

## Что произошло в живом OpenCode

На том же нормализованном плане Makora зарезервировала две родительские сессии OpenCode Desktop 2.3.0 для `auth` и `catalog`. Оба запроса `opencode/big-pickle` получили `provider.free-limit` с HTTP 429. Зависимая работа API осталась заблокированной. Прогон `953c95f4-7609-464d-b95c-c853caede3e6` находится в `attention`. Живое написание кода, реальная приёмка этих листьев и живой полный прогон ещё требуют подтверждения. Прогон использовал тот же отпечаток плана, что тестовое исполнение.

## Состояние тестов и открытые проблемы

Объединённая версия Makora прошла **68 автоматических тестов**. Покрыты 24 уровня дерева, зависимости, конфликт правок, перезапуск, сохранение готовых результатов, отмена на имитации API, точность хешей и приёмка из чата. Отдельно проверяются импорт модулей аутсорса и обновление базы версии 2 с сохранением планов. Набор можно запустить из корня клона.

```powershell
npm ci --ignore-scripts
npm test
```

Дополнительные негативные сценарии через локальный HTTP воспроизвели три случая.

| Сценарий | Фактическое поведение |
|---|---|
| Исходники изменились перед финальным решением | Приёмка блокируется. Команда продолжения может вернуть запуск в `running`, оставив узел в `reviewing` без открытого запроса. |
| Бюджет исчерпан при открытом ревью | Пакет остаётся доступен, но при отправке решения сервер возвращает `review.stale`. |
| Перепланирование одобрено без `proposal` | Сервер возвращает `ok: true`, закрывает запрос и переводит прогон в `attention` с ошибкой разбора JSON. |
