# Рабочие копии и сборка

[[00 — Makora]] · [[04 — Вложенные лаборатории]] · [[05 — E Verified Batch]] · [[10 — Эксплуатация и диагностика]]

## Что именно копируется

У самостоятельного E Verified Batch есть режимы `auto`, `worktree` и `copy`. `auto` выбирает отделённые Git worktrees для чистого корня репозитория с коммитом-основанием. При локальных изменениях, отсутствии HEAD или Git используется копия. Явный `worktree` требует пригодного репозитория. В рекурсивном режиме планировщик сначала фиксирует снимок текущих файлов, затем передаёт исполнителям копию этого снимка или собранного набора входов.

Снимок учитывает tracked, staged, unstaged и допустимые untracked файлы при наличии Git. Сравниваются текущие байты рабочего дерева. Runtime-исключения охватывают, например, `.git`, `.env*`, `node_modules`, `.venv` и Python bytecode. Опасные пути и ссылки проверяются отдельно. Базовый манифест рекурсивного запуска содержит исходный SHA, статусы Git, список исключений, карту хешей и хеш манифеста. Для удалённого или пропущенного изменения хеш содержимого может быть `null`.

## Сборка одного батча

Сборщик выбирает завершённых, индивидуально верифицированных и прошедших gate исполнителей. Затем повторно проверяет изменившиеся пути, их хеши, исходник и отсутствие конфликта между выбранными результатами. Отдельная папка сборки получает базу и разрешённые изменения. В манифесте фиксируются входной снимок, выбранные работники, результаты и хеши. `verify` сравнивает текущие файлы этой папки с манифестом и проверяет стабильность исходника. Папка и манифест создаются заново для каждого вызова.

## Сборка между батчами

Рекурсивный артефакт описывает результат одного узла.

| Поле | Для чего |
|---|---|
| `inputManifestHash` | Отпечаток исходных входов данной работы. |
| `dependencyArtifacts` | ID использованных артефактов. |
| `verificationHash` | Отпечаток доказательств проверки. |
| `changes[].path` | Нормализованный путь изменения. |
| `changes[].beforeHash`, `changes[].afterHash` | SHA-256 до и после. У добавления предыдущий хеш отсутствует, у удаления отсутствует последующий. |

Сборщик проходит по зависимостям и применяет каждый артефакт в порядке, согласованном с входами. Общие предки применяются один раз. Перед применением правки текущий хеш файла должен совпасть с `beforeHash`. Например, если один исполнитель изменил файл из A в B, следующее изменение B → C можно применить поверх B. Две независимые правки A → B и A → C дадут конфликт. Сборщик проверяет итоговые байты, регистр и конфликт файла с каталогом-предком.

Проверки выполняются в отдельной копии. Успешное завершение проверок даёт пакет ревью, связанный с точной сборкой. Перед приёмкой корня текущая папка проекта сверяется с исходным снимком. Папка принятой сборки отображается в панели. Ручной перенос согласованных файлов и проверки в исходном проекте — отдельный этап процесса.

## Какие доказательства читать

- Принадлежность работы — ID прогона, попытки, родительской и дочерней сессий, канонический путь копии.
- Что было изменено — diff, карта затронутых путей и SHA-256 содержимого.
- Почему результат пригоден — отчёты gate, `assemble`, `verify` и вывод тестов по критериям.
- Что именно принято — ревизия, ID запроса, решение и хеши сборки и проверки.
