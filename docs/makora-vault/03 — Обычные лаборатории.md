# Обычные лаборатории

[[00 — Makora]] · [[02 — Проекты и задачи]] · [[04 — Вложенные лаборатории]] · [[07 — Дашборд CLI и данные]]

Обычная лаборатория проверяет гипотезу через локальное демо. Например, при восстановлении после обрыва связи можно показать искусственный сбой и проверить, что данные возвращаются в ожидаемое состояние.

## Полный цикл

1. **Предложение.** `lab.propose` сохраняет название, сценарий, критерии, области `modulePaths` и `demoPaths`, при наличии — доказательство. Пути модуля и демо должны быть раздельными. Карточка начинается в `proposed`.
2. **Решение по идее.** В браузере пользователь выбирает `approved` или `rejected`. Одобрение разрешает подготовить демо.
3. **Подготовка исполнения.** Разрабатываются отдельный функциональный модуль и демонстрация. Для них удобно применять разные зоны записи и сохранять diff каждого исполнителя. См. [[05 — E Verified Batch]].
4. **Настройка.** `lab.configure` сохраняет `cwd`, `runtime`, `args` и `evidence`. Поддерживаются `node` и `python`. Аргументы передаются массивом, процесс стартует без интерпретации аргументов оболочкой.
5. **Запуск.** Кнопка в браузере вызывает `lab.start`. Дашборд проверяет владельца каталога, выделяет порт и временный каталог данных, запускает процесс и отслеживает готовность.
6. **Проверка пользователем.** В панели можно открыть демо и воспроизвести сценарий. Выбор `accepted` или `changes_requested` доступен после подтверждения готовности. Запущенный процесс можно остановить.

Так выглядит массив аргументов для демонстрационного сервера.

```json
["demo/server.cjs", "--port", "{port}", "--data", "{data}"]
```

`{port}` заменяется выделенным портом, `{data}` — путём к временным данным. Порт также доступен через `PORT`. Каталог запуска должен быть внутри зарегистрированного проекта или в проверенном Git worktree этого проекта. Хранилище данных панели и каталог её кода исключены. Расположение обычной копии в каталоге прогонов само по себе не доказывает её принадлежность.

## Как подтверждается готовность

Когда аргументы содержат `{port}`, дашборд проверяет возможность подключения к `127.0.0.1` на выделенном порту. Без этого параметра готовность означает, что процесс устойчиво прожил начальный интервал. Проверка TCP или живого процесса подтверждает запуск, а качество сценария оценивается пользователем по критериям. Ошибка старта, ранний выход или истечение времени готовности фиксируются отдельно.

У карточки есть две независимые оси состояния. `proposed`, `approved`, `configured`, `ready`, `accepted`, `changes_requested` и `rejected` описывают жизненный цикл карточки. `running`, `ready`, `stopped`, `failed`, `unverified` и `not_started` отражают состояние процесса. После перезапуска дашборд снимает неподтверждённую готовность предыдущего процесса.

После замечаний повторное `lab.propose` с тем же ID создаёт новую ревизию при изменении содержания. Настройки запуска и подтверждение готовности сбрасываются. Принятие демо фиксирует решение по сценарию. Для внедрения берутся проверенные файлы модуля и его тестов, а демонстрационные файлы остаются отдельно. См. [[06 — Рабочие копии и сборка]].
