# Шаблоны действий

[[00 — Makora]] · [[02 — Проекты и задачи]] · [[03 — Обычные лаборатории]] · [[04 — Вложенные лаборатории]] · [[07 — Дашборд CLI и данные]]

Поля в угловых скобках нужно заменить значениями своего проекта. Каждый JSON-блок сохраняется в отдельный UTF‑8 файл. После запуска панели передать его можно через `node ./dashboard/control.cjs action "<файл.json>"`.

## Регистрация проекта

```json
{
  "action": "project.add",
  "name": "Локальный каталог",
  "path": "D:/Projects/catalog"
}
```

Идентификатор проекта возвращается в результате. По умолчанию фазой станет `brief`.

## Обычная лаборатория с демо

```json
{
  "action": "lab.propose",
  "projectId": "<project-id>",
  "title": "Повторное подключение",
  "scenario": "Открыть демо, оборвать соединение, восстановить соединение",
  "criteria": ["Данные восстановлены после повторного подключения"],
  "modulePaths": ["src/reconnect.cjs"],
  "demoPaths": ["demo/"]
}
```

После одобрения идеи через панель настрой уже подготовленное демо.

```json
{
  "action": "lab.configure",
  "projectId": "<project-id>",
  "id": "<lab-id>",
  "cwd": "D:/Projects/catalog",
  "runtime": "node",
  "args": ["demo/server.cjs", "--port", "{port}", "--data", "{data}"],
  "evidence": "Путь к проверенному diff и журналу запуска"
}
```

Команды запуска, остановки и приёмки находятся в браузере.

## Минимальное вложенное дерево

Первый тест уже должен существовать, а исполнитель создаёт только `catalog.cjs`. Для более глубокого дерева добавь ветки с собственными тестами. Для межветочных зависимостей укажи `dependsOn` на ветке или листе.

```json
{
  "action": "plan.put",
  "projectId": "<project-id>",
  "id": "catalog",
  "title": "Хранилище каталога",
  "requirements": "Сохранить данные и вернуть их в порядке добавления",
  "nodes": [
    {
      "id": "root",
      "kind": "branch",
      "parentId": null,
      "title": "Проверенный каталог",
      "criteria": ["Интеграционный тест каталога проходит"],
      "checks": [{"executable": "node", "args": ["--test", "catalog.test.cjs"]}]
    },
    {
      "id": "catalog-store",
      "kind": "leaf",
      "parentId": "root",
      "title": "Хранилище",
      "goal": "Реализовать хранение элементов",
      "contract": "Реализовать интерфейс, который использует catalog.test.cjs",
      "criteria": ["Записи возвращаются в порядке добавления"],
      "checks": [{"executable": "node", "args": ["--test", "catalog.test.cjs"]}],
      "model": "opencode/big-pickle",
      "profile": "opencode/big-pickle",
      "writeScope": ["catalog.cjs"],
      "dependsOn": []
    }
  ]
}
```

Пример фиксирует имеющийся профиль. Для фактического запуска нужна утверждённая пользователем модель. Пользователь проверяет план и нажимает «Утвердить и запустить».

## Получение и сдача ревью из чата

```json
{
  "action": "plan.review.pending",
  "projectId": "<project-id>",
  "runId": "<run-id>"
}
```

После проверки diff, критериев и тестов подставь значения из возвращённого пакета.

```json
{
  "action": "plan.review.decide",
  "projectId": "<project-id>",
  "runId": "<run-id>",
  "requestId": "<request-id>",
  "assemblyHash": "<assembly-sha256>",
  "verificationHash": "<verification-sha256>",
  "decision": "approved",
  "findings": ["Проверил diff, повторил тесты каталога в сборке"]
}
```

Для положительного решения по запросу типа `replan` дополнительно нужен `proposal` — объект с полным обновлённым планом. Перед отправкой следует сверить исходные требования, бюджет, команды, модель и области записи. В [[11 — Пилот и границы проверки]] описано, что сейчас происходит при пропуске этого поля.
