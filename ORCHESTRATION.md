# Оркестрация Codex и OpenCode

Практики других систем и методика сравнения описаны в [RESEARCH.md](RESEARCH.md).

Codex в текущем чате остаётся оркестратором. Его модель выбирает пользователь в интерфейсе Codex. По умолчанию используется согласованная бесплатная модель исполнителей `opencode/big-pickle`. Явный выбор другой доступной модели в запросе имеет приоритет. При ошибке модели сообщи причину, сохрани сессии и результаты. Не переключай провайдера автоматически. Используй существующую авторизацию OpenCode Desktop. Процессу нужны доступ к рабочим копиям в `%LOCALAPPDATA%\Codex\OpenCode workers` и подключение к локальному сервису OpenCode. Если настройки Codex блокируют запуск, соблюдай штатный процесс разрешений и сообщи пользователю, какой шаг заблокирован.

## Обязанности и четыре этапа

В начале Codex читает четыре существующих `SKILL.md` из настроенного каталога навыков Codex (например, `C:/CodexData/skills`) по порядку ниже. Для этого процесса достаточно этих четырёх навыков. Инструкции выбранного проекта и пользователя имеют приоритет. Разрешение на разработку покрывает локальный запуск агентов и перенос принятого результата. Коммиты, merge, публикация, миграции и production-действия требуют отдельного указания пользователя.

1. **`architecture-guardrails` — Codex.** Определи границы задачи, затронутые модули, контракт между исполнителями и сценарии приёмки. Зафиксируй замысел соразмерно задаче. Исполняемые проверки границ, если нужны, включи в задание OpenCode.
2. **`to-tickets` — Codex.** Дай каждой задаче ID, цель, затрагиваемые файлы, контракт, ограничения, зависимости, критерии приёмки и проверки. Закрепи независимые случаи приёмки за конкретными задачами и зафиксируй их формулировки до запуска; после ответов исполнителей критерии не переписывай. Выбирай число исполнителей адаптивно: одна задача для малой правки, два независимых задания для существенной работы, третий слот — только если независимость действительно подтверждена. Один файл или каталог имеет одного владельца: общие файлы, конфигурацию и миграции отдавай одному исполнителю. Для проверок указывай локальную изолированную БД и отдельные порты, чтобы параллельные задачи не конфликтовали за общие ресурсы.
3. **`implement` — OpenCode.** Архитектуру и контракты сначала фиксирует Codex. Затем один агент OpenCode-оформления владеет общими контрактами, точкой входа приложения и smoke-проверкой; Codex проверяет этот каркас и только после этого фиксирует общий baseline и запускает параллельных исполнителей с непересекающимися `writeScope`. По умолчанию после `to-tickets` используй групповой запуск `batch` (см. ниже). Codex снимает исходное состояние и назначает исполнителей. Весь код приложения, тесты, скрипты, конфигурацию реализации и связующий код пишут агенты OpenCode. В задании передай путь к навыку `implement` и адаптации ниже. Каждый исполнитель запускает проверки своей задачи и возвращает изменённые файлы, команды, результаты и ограничения. Перед переносом Codex собирает принятые изменения командой `assemble` и запускает интегрированные тесты из изолированной сборки; только после успешной сборки и проверки выполняется перенос точных файлов. Зависимую интеграцию отдавай отдельной задачей, например подключение интерфейса и логики после переноса обеих принятых частей.
4. **`code-review` — Codex.** Финальное ревью и интегрированный прогон тестов делает основной Codex, а не исполнитель. Проверь фактический diff относительно baseline, исходное задание, границы модулей, новые файлы, удаление и переименование, регрессии и тесты. Сведи наблюдения в матрицу критериев: критерий, ожидаемый факт, фактический результат, серьёзность, доказательство и владелец. Серьёзность должна быть действием: blocker — вернуть задание и сохранить логи; major — отдельная итерация исправления с повторным ревью; minor — принять с пометкой в отчёте. Доказательство — конкретный путь в `<run>` (`summary.json`, `*.diff`, `*.export.json`, `*.process.log`), команда и её вывод. Запускай проверки сам и смотри их вывод. По замечаниям выдай OpenCode конкретное задание на исправление и повтори ревью. После двух попыток расследуй причину и уточни задание или сообщи о блокере. Код и в этом случае пишет OpenCode. После принятия запускай проверки исходного проекта и переходи к следующей зависимой задаче.

Codex может писать архитектурные заметки, задания и отчёты, читать и сравнивать файлы, вызывать инструменты и запускать проверки. Интеграция с его стороны — перенос проверенных файлов или чистое применение готового патча. Любое изменение содержания патча, разрешение конфликтов, форматирование кода и добавление тестов выполняет OpenCode. Если исходный проект изменился параллельно или патч требует доработки, подготовь свежую копию и передай конфликт OpenCode. При недоступности OpenCode сообщи блокер. В этих условиях рабочий результат остаётся привязан к конкретному исполнителю и его сессии.

Шаблон задания для исполнителя:

> Этап implement. Прочитай инструкцию `implement/SKILL.md` из настроенного каталога навыков, если файл доступен. Действуют следующие адаптации: работай только в своей копии и в назначенных файлах, выполни проверки по заданию, верни изменения на ревью Codex. Коммиты не создавай, дополнительные навыки не подключай.
> ID, цель, границы записи, контракт, критерии приёмки и проверки: [из задачи Codex].
> Отчёт: ID сессии, список файлов, выполненные команды и результаты, оставшиеся ограничения.

## Групповой запуск (batch) — режим по умолчанию

Команда:

```powershell
node ./workers.cjs batch "<корень проекта>" "<plan.json>"
```

План — UTF-8 JSON (BOM допускается):

```json
{
  "workers": [
    {
      "name": "server",
      "model": "opencode/big-pickle",
      "prompt": "SC-01. Реализовать HTTP/SQLite-контракт. Независимый случай приёмки: POST /items создаёт запись во временной SQLite-БД и возвращает 201. Проверки: python -m unittest discover -s tests -v с локальной БД и портом 19101. Вернуть ID сессии, файлы, команды, результаты и ограничения.",
      "agent": "general",
      "writeScope": ["app.py", "studserver/", "tests/", "requirements.txt"]
    },
    {
      "name": "ui",
      "model": "opencode/big-pickle",
      "prompt": "SC-02. Реализовать браузерный интерфейс. Независимый случай приёмки: интерфейс отображает список данных, полученных от локального тестового сервера на порту 19102. Проверки: открыть список в браузере и проверить разметку на мобильной ширине. Вернуть ID сессии, файлы, команды, результаты и ограничения.",
      "agent": "general",
      "writeScope": ["web/"]
    }
  ]
}
```

- `model` по умолчанию `opencode/big-pickle`, `agent` по умолчанию `general`. Ошибка бесплатной модели не вызывает переключение на другую модель: сообщи причину и сохрани сессии.
- `writeScope` по умолчанию указывай в каждом задании. Это массив путей файлов (`app.py`) или каталогов с завершающим `/` (`studserver/`) относительно корня проекта. Пути нормализуются на `/`, сравнение регистронезависимое по правилам Windows. Пропуск поля допустим только для старых планов: проверка зоны для такого исполнителя отключается, но конфликты по фактически изменённым файлам всё равно проверяются. Явно указанные `null` или `[]` отвергаются: так попытка выключить gate не пройдёт незаметно. Зона включается в текст задания, который получает исполнитель.
- До любых действий проверяется весь план: типы полей, непустой полный текст задания, уникальность имён, не более трёх одновременных исполнителей. Элементы `writeScope` не должны быть пустыми, абсолютными, с обходом `..`, содержать `\`, подстановочные знаки, дисковые префиксы, зарезервированные имена Windows или завершающие пробелы/точки; дубликаты внутри одного массива отвергаются. План с четырьмя и более рабочими или с пересекающимися зонами двух исполнителей отвергается до создания копий, включая коллизию файла и каталога-предка (`src/a.ts` против `src/`) или объявленного точного файла-предка (`a.txt` против `a.txt/sub.txt` и `a.txt/subdir/`). Несвязанные пути с общим префиксом (`a.txt` и `a.txt.bak`, `a/` и `a2/`) совместимы. План без `writeScope` работает как раньше.
- В одном `batch` только независимые задания с зафиксированными случаями приёмки. Один файл или каталог закрепляется за одним исполнителем, общие файлы отдавай одному исполнителю. Выбирай один или два рабочих адаптивно по объёму независимой работы. Каждая задача использует локальную изолированную БД и собственный порт. Зависимые задачи готовь отдельным batch только после того, как Codex проверил и принял предыдущий результат.
- **Проверка зоны — post-execution, а не песочница.** Gate работает после сканирования файлов исполнителей: он ищет правки вне `writeScope` (включая новые и удалённые файлы) и конфликты между всеми исполнителями по факту, даже если зоны не объявлены. Конфликт — это один и тот же путь без учёта регистра или случай, когда один изменённый путь является каталогом-предком другого (`pkg` против `pkg/index.js`). Границы компонентов уважаются: `pkg/a.ts` и `pkg2/a.ts` не конфликтуют. Затронутые исполнители получают статус `blocked`, весь batch — `incomplete` и ненулевой код выхода; полный список путей и владельцев остаётся в `<run>/summary.json`, а в чат выводится короткая причина с ограниченным числом путей. Ошибка подсчёта изменённых файлов тоже блокирует batch. Исходный проект gate никогда не меняет. Рабочие копии дают изоляцию правок, **но не являются изоляцией ОС**: это не security sandbox, политики проекта и разрешения OpenCode продолжают действовать.
- Снимок, локальный сервис и отдельные копии создаются так же, как в `prepare`. Никакого дополнительного координатора-модели и никакого автоматического копирования в исходный проект нет. При нескольких исполнителях реальные процессы запускаются параллельно через `spawn`; бюджет — 30 минут на исполнителя (переопределяется только локально через `OPENCODE_BATCH_BUDGET_MS`).
- Потоки stdout/stderr процессов остаются в файлах `<run>/<name>.process.log`. В чат выводится один короткий структурированный JSON-отчёт. Полный отчёт сохраняется в `<run>/summary.json`.

### Режимы рабочего пространства

Поле `workspace` в плане (или переменная `OPENCODE_WORKSPACE_MODE` для `prepare`): `auto` по умолчанию, также допустимы `copy` и `worktree`.

- `auto` использует настоящие отсоединённые (`--detach`) git worktree — по одному на исполнителя, все на одном зафиксированном `HEAD` — **только** если источник является корнем репозитория, есть `HEAD` и нет отслеживаемых или неигнорируемых незакоммиченных изменений. Во всех остальных случаях (грязный проект, проект без первого коммита, не репозиторий, подкаталог репозитория) используется точная копия снимка. Коммиты в проекте в таком случае не создаются.
- Явный `worktree` при непригодности источника завершается ошибкой с причиной; режим `copy` можно запросить вручную. `baseline` всегда остаётся неизменяемой обычной копией: в режиме worktree она создаётся из первого worktree, чтобы разница в `core.autocrlf` не выглядела как правка исполнителя. Перед запуском исполнителей дополнительно сверяются отсоединённый HEAD (`--abbrev-ref HEAD === HEAD` и SHA равен зафиксированному) и совпадение начального инвентаря каждого worktree с копией `baseline`; при расхождении команда падает без вызовов модели. Никаких commits, reset, merge и автоматической уборки worktree скрипт не выполняет; зарегистрированные worktree остаются для проверки, удаляет их пользователь вручную.
- В `<run>/manifest.json` и `<run>/summary.json` фиксируются `mode`, `baseSha`, `workspace` и пути `source`/`baseline`/`workers`. В инвентаре изменений не участвуют каталоги и файлы управления `.git`, прежние runtime-исключения (`.codex`, `.bridge`, `.mcp.json`, `node_modules`, `.venv`, `__pycache__`, `.env*`, bridge-плагин), Python bytecode (`*.pyc`, `*.pyo`) и файлы, игнорируемые Git по правилам исходного проекта. Сгенерированный код, который не попадает под эти правила, остаётся в зоне проверки.

### Проверка результата batch

Успех фиксируется только после проверки реальной дочерней сессии, а не по коду выхода CLI. Для каждого исполнителя скрипт читает `<run>/<name>.jsonl`, находит родительскую сессию и ровно один ID дочерней сессии по событиям `background_wait`/`subagent`, затем запрашивает `opencode-cli.exe session export <child-id>` из рабочей копии. Принимается только сессия с совпадающим `parentID`, завершённым состоянием и без терминальной ошибки. Таймаут и ненулевой код выхода дают статус `failed`; отсутствие ID, расхождение родителя или ошибка экспорта дают статус `unverified`. Любой такой результат означает ненулевой код выхода всей команды. Внутренний CLI получает бюджет меньше внешнего на время проверки сервиса и грацию, поэтому завершается первым; при таймауте удалённый дочерний агент может продолжать работу, проверь его сессию вручную. Остальные исполнители дожидаются завершения, частичный отчёт сохраняется.

В `summary.json` для каждого исполнителя есть `source`, `baseline`, `run`, `status`, `model`, `workerPath`, `parentSessionID`, `childSessionID`, `elapsedMs`, `log`, `processLog`, `exportLog`, `changedPaths` (полный список, включая добавленные и удалённые файлы), путь к полному diff, а также короткое `selfReport` с пометкой `selfReported: true`. Добавлены `writeScope`, `outOfScopePaths`, `qualityGate` (причины блокировки с владельцами), `startedAt`/`endedAt` и `changedPathsError`. На верхнем уровне есть `qualityGate`, `durationMs` (стенное время batch) и `timing`: `longestWorker`/`longestWorkerMs`, а также `parallel` (`activeSumMs`, `unionMs`, `parallelWorkerMsSaved`, `parallelismRatio`) — только когда все процессы зафиксировали момент завершения и исполнителей как минимум двое; `unionMs` — время, покрытое хотя бы одним процессом (объединение интервалов), `parallelWorkerMsSaved` — сумма активного времени процессов минус `unionMs`, то есть сэкономленное стенное время, а не длительность одновременной работы двух и более исполнителей; иначе `longestWorker`, `longestWorkerMs` и `parallel` равны `null` с причиной в `note`. `elapsedMs` — время активного процесса от запуска до события `exit`/`close`, а не время ожидания соседей или экспорта сессии: задача в 5 минут не должна получить +19 минут просто потому, что проверка batch закончилась позже. В stdout список путей и причины ограничены и сопровождаются счётчиком; полный список остаётся на диске.

### Матрица критериев приёмки

| Критерий | Ожидаемый факт | Доказательство | Серьёзность | Действие Codex |
| --- | --- | --- | --- | --- |
| Результат исполнителя | Ровно один дочерний ID, совпадающий `parentID`, завершённый outcome без ошибок | `summary.json`, `<name>.export.json` | blocker | Сохранить логи, перевыпустить задание с тем же ID |
| Зона записи | Все `changedPaths` внутри `writeScope`, включая новые и удалённые файлы | `outOfScopePaths`, `<name>.diff` | major | Новый batch с исправленной зоной, принятые файлы не трогать |
| Один владелец файла | Нет общего пути и нет пары «файл — каталог-предок» у двух исполнителей | `qualityGate.conflicts` в `summary.json` | blocker | Разделить зоны и повторить batch |
| Тесты | Проверки каждого исполнителя пройдены, интегрированный набор прошёл у Codex | `<name>.process.log`, вывод команд в чате | major | Отдать OpenCode задание на исправление, повторить прогон |
| Изоляция ресурсов | Локальная БД и отдельные порты у каждой задачи | Конфигурация и логи тестов | major | Перенастроить тесты, исключить общие состояния |
| Время | `elapsedMs` отражает активный процесс, не ожидание | `startedAt`, `endedAt`, `timing` | minor | Уточнить отчёт; на решения по коду не влияет |

Финальное решение принимает основной Codex после просмотра матрицы, полного diff и интегрированного прогона тестов; статус `ok` сам по себе основанием для переноса не является.

Смотри фактические изменения, а не обещания агента:

```powershell
node ./workers.cjs diff "<run>" server
```

Команда печатает полный `--no-index` diff между `baseline` и копией `server`. Полный diff также сохранён в `<run>/server.diff`. Перед переносом сверь затронутые файлы исходного проекта с `baseline`, а для новых файлов проверь, что пользователь не создал свои по тем же путям. Переноси только принятые изменения и запусти проверки сам. Скопировать результат в исходный проект автоматически никто не будет.

### Сборка проверенных изменений (assemble) и изолированные тесты

```powershell
node ./workers.cjs assemble "<run>" server ui
node ./workers.cjs verify "<run>/assembly"
```

`assemble` принимает только явно перечисленных исполнителей, у которых есть индивидуально завершённая и верифицированная запись в `summary.json`; заблокированные исполнители не мешают сборке других, но сами не могут быть выбраны. Повторный выбор того же имени, пересекающиеся или конфликтующие правки отвергаются существующей логикой путей. Сборка начинается с независимой копии `baseline`, затем поверх неё побайтово накладываются добавления, изменения и удаления выбранных исполнителей. Перед наложением сверяются все зафиксированные хеши `baseline` (включая файлы, которые никто не менял), сохранённые хеши артефактов исполнителей и состояние источника: затронутые пути обязаны остаться теми же regular-файлами, а новые неигнорируемые файлы недопустимы. Небезопасные пути, каталоги и символические ссылки на путях из задания отвергаются. Повторная сборка создаёт свежие каталоги `assembly-2`, `assembly-3` и манифесты `assembly-2.json` и т. д.; существующие сборки не перезаписываются. При любом несоответствии команда завершается с ошибкой и оставляет файлы для осмотра — автоматического переноса и автоматической уборки нет.

`<run>/assembly.json` (или `<run>/assembly-N.json`) содержит затронутые файлы с хешами `before`/`assembled`, полные хеши сборки, режим, `baseSha` и список исполнителей. `verify <assembly>` находит подходящий манифест по каталогу, повторно сравнивает сборку с ним и проверяет источник на параллельные правки и новые пути; статус `stale` или `failed` означает ненулевой код выхода. Codex запускает независимые интегрированные тесты из выбранного каталога сборки, сравнивает их с ожидаемыми сценариями приёмки и только после этого вручную переносит точные файлы в исходный проект.

### Целевой повтор неудавшегося исполнителя (retry)

```powershell
node ./workers.cjs retry "<run>" <worker> ["<prompt.txt>"]
```

Повтор допускается только для поименованного исполнителя и только в его же копии/снимке. Для незавершённого исполнителя проверяются зафиксированные хеши артефактов; для завершённого, но отклонённого ревью, обязателен явный файл пересмотренного задания, отличный от исходного. Завершённый результат других исполнителей и их файлы не трогаются: при успехе `summary.json` обновляется только для выбранного имени. Повтор продолжает ту же дочернюю сессию через `opencode run --session <child-id>` без подмены агента, пишет новый лог `<name>.retry-N.jsonl` и отчёт `<name>.retry-N.report.json` с фактическими `startedAt`/`endedAt`. Верификация строгая: в логу должен быть только записанный child ID, экспорт должен подтвердить исходную пару parent/child, а новое завершённое состояние сессии должно наступить после начала повтора. Одновременный повтор одного `run` отвергается блокировкой `retry.lock`.

**Ограничение установленного OpenCode Desktop 2.3.0:** продолжение сессии не гарантировано — CLI может отвергнуть `--session`, не выпустить событие дочерней сессии или зависнуть. Автоматического свежего запуска с `--agent build` больше нет: при любой не подтверждённой идентичности сессии, таймауте, ошибке запуска или продолжающемся выполнении команда явно сообщает `Use a fresh scoped batch.` и завершается с ошибкой. Файлы, логи и отчёт остаются для осмотра; новый batch готовится вручную с уточнённым заданием.

### Какие проверки являются доказательством

Самоотчёт исполнителя и зелёный код выхода CLI доказательством не являются. Доказательство результата исполнителя — export дочерней сессии с совпадающим `parentID`, завершённым outcome, инвентарь изменённых файлов, `<name>.diff` и результат gate в `summary.json`. Доказательство интеграции — интегрированные тесты, запущенные Codex из `<run>/assembly`, и их вывод в чате. Финальное доказательство — те же тесты в исходном проекте после ручного переноса точных файлов. Локальные smoke-проверки оформления и каждого исполнителя фиксируются в `<name>.process.log` и считаются дополнительными, но не заменяют интегрированную проверку сборки.

Для доработки подготовь свежий batch: сохрани старые логи и `summary.json`, составь новый план с теми же или уточнёнными текстами заданий, включив предыдущий результат и замечания ревью. Не переиспользуй каталог `run` и не перезаписывай существующие логи. Если исходные файлы изменились, явно укажи в задании, какие изменения нужно сохранить.

## Запуск и проверка (ручной fallback)

1. Определи корень проекта. До изменений запиши `git rev-parse --verify HEAD` и исходное состояние (staged, unstaged и untracked). Для проекта без первого коммита явно отметь отсутствие `BASE_SHA` и используй снимок файлов. Для каждой зависимой итерации бери снимок после приёмки предыдущей.
2. Основной путь — `batch` из раздела выше. Ручной путь: `node ./workers.cjs prepare "<корень проекта>" worker-a worker-b [worker-c]`. Команда вернёт путь `run`, исходный снимок `baseline` и пути копий. Допускается и одно имя, например `prepare "<корень>" worker-a` — для одного реального исполнителя `reserve` больше не нужен. Команда работает с текущим содержимым файлов, включая ещё не закоммиченные изменения. Первый коммит не требуется. Снимок опускает символические ссылки, игнорируемые Git незатреканные файлы, локальные `.env*`, распространённые каталоги зависимостей и настройки запуска Bridge/Codex. Учитывай эти исключения при назначении проверок.
3. Для ручного пути запиши в каталог `run` по UTF-8 текстовому файлу с заданием для каждого исполнителя. Запусти по отдельному процессу `node ./workers.cjs run "<run>" worker-a opencode/big-pickle "<run>/worker-a.txt"` для каждого исполнителя. Последним аргументом можно передать ID другого настроенного субагента, например `explore` для исследования. Параллельно запускай только независимые задания. Скрипт открывает сессию на локальном сервере OpenCode Desktop в копии исполнителя. Родительский агент OpenCode запускает в этой копии дочернего субагента `general` по умолчанию. В OpenCode видны родительская сессия **Codex worker: worker-a** и запуск дочерней работы. Отдельные копии дают изоляцию правок. Политики проекта и разрешения OpenCode продолжают действовать.
4. Дождись завершения, сохрани ID дочерних сессий и проверь реальные файлы. В `<run>/<имя>.jsonl` доступны события работы. Если последним событием остался `background_wait`, проверь итог дочерней сессии в OpenCode Desktop или через `opencode-cli.exe session export <ID>` из её рабочей копии. Исполняемый файл находится в `%APPDATA%\ai.opencode.desktop\cli\<версия>-x64\opencode-cli.exe`. Если родитель не запустил дочернюю сессию или она завершилась ошибкой, явно зафиксируй это и проверь пригодность результата. Для просмотра изменений выполни `node ./workers.cjs diff "<run>" worker-a`. Для просмотра сессии в OpenCode Desktop открой путь её рабочей копии из manifest.
5. Перед переносом проверь каждый diff и сравни затронутые файлы исходного проекта с baseline. Для новых файлов также проверь, что по тем же путям пользователь не создал свои файлы. Переноси только принятые изменения. После переноса проверь итоговые файлы и запусти нужные тесты сам. Сообщи, что сделано, какие проверки прошли, какие ограничения остались, а также названия родительских сессий и ID дочерних агентов OpenCode. Храни копии локально для ревью.

Этот процесс использует общий сервер OpenCode Desktop напрямую, чтобы адресовать рабочие копии по пути. Переносить проектную конфигурацию Open Agent Bridge в каждый новый проект не требуется.
